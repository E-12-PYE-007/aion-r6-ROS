Safety Layer Design

verified marks a claim I checked by reading the code or running it against the real code / recorded ESDF bag (the check is named). unverified marks anything I have not checked. Branch: safety-layer, based on origin/main at 3a52fc7.

1. Overview

The safety layer is a ROS 2 node that takes a VLA action chunk and outputs cmd_vel, keeping the robot outside an ESDF safety margin around obstacles. Two interchangeable implementations exist, each launched on its own: a CBF node and an MPC node. The VLA is treated as obstacle-blind; the safety layer is what makes the result safe.

  • CBF: pure-pursuit nominal command, then a small QP that returns the nearest command keeping a point ahead of the robot outside the margin. One node, nominal and filter inside it.
  • MPC: nonlinear MPC tracking the chunk with a slacked ESDF-distance constraint, plus a soft low-velocity floor (weight 100, threshold 0.15 m/s, horizon N=14 at 0.2 s).

Both share ESDF handling, pure-pursuit geometry, frame transforms, constants for limits, and the output topic.

   /vla/action_chunk ─┐
   /odom             ─┼─►  safety layer node (cbf | mpc)  ─►  cmd_vel
   /nvblox_node/static_map_slice ─┘        └─►  safety_layer/slack (debug)

Slack units differ. The CBF publishes cbf/slack: the slack s in ddt(h) + s ≥ -αh, in m/s. The MPC publishes mpc/max_slack: the largest ESDF-margin slack over the horizon, in metres. Both controllers currently use odom as the odom frame, and the bench bag's frame is odom verified (read from the first message), so the ESDF–odom transform is the identity on the bench.

4. Shared code

Everything both controllers need lives in safety_layer/common:

  • constants.py: limits, ESDF patch geometry, safety margin, control period, pure-pursuit tuning, topic and frame names.
  • esdf_map.py: EsdfMap.store reshapes a slice and replaces unknown cells with 2.0 m; get_patch cuts a square patch centred on a map-frame point, filling out-of-bounds with 2.0 m; patch_at does the odom → ESDF-frame transform lookup and returns the patch and the frame yaw.
  • esdf_spline.py: the bicubic B-spline ESDF lookup used inside both the QP and the NLP, including the coefficient shift that makes out-of-patch queries read as free space.
  • frames.py: quaternion to yaw, angle wrapping, planar pose transform.
  • pure_pursuit.py: the obstacle-blind nominal command. It anchors to the pose at the chunk's first sight (seq_num change), Hermite-interpolates the 8 waypoints (10 samples per segment), finds the first sample beyond the 0.3 m lookahead, turns it into a curvature, scales speed to V_MAX / (1 + K·|κ|), and saturates v and omega together so the turning radius is preserved. If no sample is beyond the lookahead it returns (0, 0). Used by the CBF node; the MPC does not use it. The standalone control/pure_pursuit_controller.py still has its own copy.

verified When the code was ported, it computed exactly what the original per-controller code did: on 40 real ESDF patches the CBF output (v, omega, h, slack) differed by 0.00e+00 from the original, with the constraint active in 6 of them; the MPC's first command and predicted states were identical on 12 solves; the ESDF patches were identical; and 60 pure-pursuit steps over 6 chunks matched exactly. The CBF filter was changed deliberately after that (section 5); the rest is unchanged.

5. CBF node

One node. Each tick (about 15 Hz): compute the nominal (v, omega), cut the ESDF patch around the robot, solve the QP, publish cmd_vel and slack. The QP is a small convex problem solved fresh each call with CasADi qrqp.

ParameterValueMeaning
SAFETY_MARGIN_M + CBF_EXTRA_MARGIN_M0.20 + 0.15The barrier's margin. The extra 0.15 m covers the robot's centre passing closer to an obstacle than the lookahead point does when it turns past it.
LOOKAHEAD_M0.4The barrier is evaluated at this distance ahead of the robot. At the robot's centre omega has no effect on ddt(h); ahead of it, turning moves the point sideways, so the QP can steer as well as brake.
CBF_ALPHA2.0Class-K gain: smaller brakes earlier and more gently
CBF_WEIGHT_OMEGA0.003Cost of changing omega from the nominal. It is nearly free so the filter can steer round an obstacle the nominal points straight at; with a large weight it can only brake and the robot stops in front of it.
CBF_SLACK_WEIGHT1000Keeps the QP feasible if the robot is already inside the margin

The formulation and derivation stay in cbf_formulation.pdf on the CBF-obstacle-avoid branch. Section 14 says what each knob does and how these values were chosen.

The barrier derivative (a defect fixed after the port)

The ESDF patch is centred on the robot's current position and the lookup uses the offset from that centre. The original code differentiated the barrier with respect to the robot pose while using that same pose as the patch centre, so the dependence on the robot's position cancelled: the QP's coefficient on forward speed, Lg_h_v, came out as about 0.00 and the filter could never brake for an obstacle ahead; it could only steer, limited to 0.3 rad/s. Now the patch centre is held fixed while the lookahead point moves. verified By finite differences through the same patch, dh/dx is −0.95 on the approach (the old code effectively used 0), and an independent solve of the same QP (SLSQP) gave the same answer as qrqp, so the solver was never the problem. The MPC is not affected, because its states are decision variables measured from a fixed patch centre.

6. MPC node

From MPC-obstacle-avoid, including the low-velocity floor. Solver: CasADi with IPOPT (IPOPT_MAX_ITER = 300). Horizon: N = 14 steps at 0.2 s, about 2.8 s, matching the chunk's own 8 × 1/3 s span.

ParameterValueMeaning
LOW_V_WEIGHT100Soft stage cost on max(0, LOW_V_THRESHOLD - v)²
LOW_V_THRESHOLD0.15 m/sHalf of V_MAX
SLACK_WEIGHT1000Slack on the ESDF margin
MAX_CONSECUTIVE_SOLVE_FAILURES3Stop publishing solver output after this many failed ticks in a row

The obstacle-avoidance limits of this formulation (it stops rather than detours when an obstacle is close to dead-on with the reference, unless the low-velocity floor is on) are documented in MPC_FINDINGS.md on the MPC-obstacle-avoid branch. That document stays on that branch.

7. ESDF patch

Both controllers use a 22 × 22 patch at 0.1 m, the deployment voxel size. Both build a bicubic B-spline over the patch, so the cell count sets the size of the problem.

Quantity22 cells @ 0.1 m44 cells @ 0.1 m
Patch side2.2 m4.4 m
Half-patch (reach from robot)1.1 m2.2 m
Spline coefficients4841936

verified arithmetic, run in a script. Does 1.1 m reach far enough?

  • CBF: the barrier is evaluated 0.25 m ahead, and the margin is 0.20 m, so it looks about 0.25 + 0.20 = 0.45 m out. Well inside 1.1 m.
  • MPC: the furthest the horizon can reach is V_MAX × N × dt = 0.3 × 14 × 0.2 = 0.84 m. Inside 1.1 m.

Sim node

  • Integrates the last cmd_vel with forward-Euler unicycle kinematics on a 50 Hz timer. The step is the measured elapsed ROS time (capped at 0.1 s), so the pose stays consistent with the logged t even if the timer runs late. t counts from the first step.
  • Publishes /odom and the odom → base_link transform each step.
  • Writes one CSV row per step (below), flushing every row, so a SIGINT or SIGKILL cannot lose data.
  • Stops itself after max_duration seconds of ROS time (default 30), so a run always has a bounded length and video, and the launch shuts down with it. Set it to 0 to run until stopped.
  • Holds the last cmd_vel until a new one arrives; there is no command timeout.
  • No wheel slip, motor lag or command latency. It shows what the filter logic does, not how the rover will behave on the ground.

Scenario and start-pose deltas

The default scenario is the one used throughout development: head-on at the single obstacle.

  • ESDF: safety_layer_bench_testing/rosbags/esdf_single_obs, at a hardcoded absolute path.
  • Start pose: (0.25, 0.0, 0.0) — the ESDF cone's apex, heading straight down its axis.
  • sim_robot takes dx, dy, dtheta (default 0), expressed as a delta in the odom frame from the default start. dy:=0.3 starts at (0.25, 0.3, 0).

Where the obstacle is, read from the bag verified: on-axis cells with negative distance (inside the obstacle) span x = 2.0–2.2 m, y = −0.05–0.30 m, deepest value −0.18 m. Along the axis y = 0 the ESDF is:

x [m]0.251.01.51.71.81.92.02.2
ESDF [m]1.600.850.350.150.050.00−0.050.16

So the ESDF at the robot's centre reaches the 0.20 m margin at about x = 1.65 m, 1.4 m after the start (at 0.3 m/s, about 4.7 s). The CBF evaluates its barrier at a point 0.25 m ahead of the centre, so it starts to act earlier, when the robot's centre is near x = 1.4 m.

The goal is latched 6 m along the start heading from the start position, so it moves with the deltas. dy:=0.3 is a parallel pass with the goal at (6.25, 0.3). dtheta:=20° sends the robot on a line that misses the obstacle entirely. To approach it from an angle, choose dx, dy, dtheta so the heading points at it. The plotter draws the ESDF (obstacles are the empty regions) and a dotted start–goal line so a run is easy to read.

9. Chunk generator

A single file in the debug package, depending only on aion_msgs and /odom, so ros2 run debug chunk_generator works on the real robot as well as in the bench. Its only parameter is goal_distance (default 6.0 m); the 8 Hz rate, 0.1 m spacing and 8 waypoints are constants in the file.

Algorithm

  1. On the first /odom message, latch the goal: goal = start + goal_distance · (cosθ, sinθ). This is the only parameter (default 6.0 m).
  2. At 8 Hz, take the current pose. Direction u = unit vector from the pose to the goal, and heading = atan2(u).
  3. Waypoints i = 1..8 at pose + i · 0.1 m · u, clamped so none passes the goal.
  4. Express each as a delta in the robot's own frame: rotate the offset by −θ, with relative heading = heading − θ.

The chunk is 0.8 m long, which is 2.67 s at V_MAX, matching the real chunk span verified (0.8 / 0.3).

Why it points at a far goal

The previous generator aimed at the point 0.8 m ahead on a straight line, so any lateral offset larger than 0.8 m made the chunk point sideways at the line. A goal 6 m away barely changes direction with lateral offset. Bearing of the chunk for a robot at x = 2.0 m, both generators, goal at (6.25, 0) verified (old value computed by running the old StraightPath.lookahead_point):

Behaviour to expect

  • No line to rejoin. After a detour the robot heads for the goal from wherever it ends up.
  • Dead-on is still symmetric. A robot on the line to the goal with an obstacle dead ahead gets the same chunk every tick. That is a property of an obstacle-blind VLA, not a generator fault, and it is the case the MPC struggled with, so it stays as a test.
  • Ending. Near the goal the waypoints bunch up on it and never pass it (a robot already at the goal gets 8 waypoints at zero offset; one past the goal is pointed back at it). The pure-pursuit code returns (0, 0) when no waypoint is beyond its 0.3 m lookahead, so a real controller should stop about 0.3 m short of the goal. unverified with the real controllers, which are not ported yet; with a stand-in follower that stops when the last waypoint is within 0.3 m, the robot stopped 0.300 m from the goal (see below).

Verification

verified by running the node (the script results, not just reading the code):

  • The chunk for a robot at (2.0, 0.4, 0) with the goal at (6.25, 0) matches the worked-example table above to four decimals.
  • For a robot rotated 90° the 8 waypoints, converted to the world frame, lie on the line to the goal (largest offset 1e-16 m), 0.1 m apart, all with the same heading.
  • Closed loop with the sim (start delta dy:=-0.5 dtheta:=0.3) and a throwaway follower that steers at the chunk's last waypoint: the goal latched at (5.982, 1.273), which equals 0.25 + 6·cos(0.3), −0.5 + 6·sin(0.3) computed by hand; chunks arrived at 8.00 Hz (226 published, 226 seen, seq_num stepping by exactly 1); the robot stopped 0.300 m from the goal.

10. Plotter

safety_layer_bench_testing/plot_run.py: one script, no ROS (numpy, matplotlib and ffmpeg only). It reads a CSV log and the ESDF bag named in the log's header. The bag is parsed directly, without ROS; the parser returns the same fields as rclpy on all three bags in rosbags/ verified.

Colours

  • Negative ESDF cells (inside an obstacle): empty (white).
  • Cells at or above 0: a gradient from red (at an obstacle surface) through yellow, green and cyan to blue and purple (2.0 m, the max distance). This is the rainbow ordering RViz uses for a coloured ESDF; I built it from a list of colours, so it is an approximation of RViz's palette, not a copy.
  • Unknown cells: light grey.
  • Black solid line: the obstacle boundary (ESDF = 0). Black dashed line: the safety margin (0.20 m by default, --margin).

Contents

  • Map: the robot's path so far (a faint line shows the whole run), the robot, the latest action chunk in the odom frame (anchored as in the log section), start and goal markers, a dotted start–goal line, and a readout of time, pose, v, omega, slack and the ESDF at the robot.
  • Strips below, with a time cursor: cmd_vel (v and omega), slack (axis labelled per controller from the log header), and the ESDF distance at the robot's centre with the margin dashed. The ESDF distance is a nearest-cell lookup, and unknown cells read as the max distance, as the controllers treat them.

Options and render times are in section 13. The plot assumes the ESDF frame is odom and warns if the bag says otherwise.

13. Running the bench

What works now: the sim with logging, the ESDF publisher, and the animation. Nothing publishes action chunks or runs a controller yet, so you drive the robot by publishing cmd_vel yourself. All paths are relative to the repo root, /home/djstrahan/aion-r6-vla-master/aion-r6-ROS.

Build

source /opt/ros/humble/setup.bash
colcon build --packages-select nvblox_msgs debug
source install/setup.bash

aion_msgs must be built too; it already is in this workspace. Do this once, and again after editing anything in src/debug (the install is not symlinked). The plotter does not need any of this; it runs in a plain shell.

Start the sim

ros2 launch debug sim_bench.launch.py

Defaults: start at (0.25, 0.0, 0.0), head-on at the single obstacle, esdf_single_obs, 30 s run. The terminal prints the log file it is writing (sim_logs/run_<timestamp>.csv, under the directory you launched from, so launch from the repo root to keep logs in the gitignored sim_logs/). It stops itself after 30 s (max_duration) and shuts the launch down; Ctrl-C also works at any time.

Drive it by hand

In a second terminal (with the workspace sourced):

ros2 topic pub -r 10 cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.3}, angular: {z: 0.0}}"

The robot moves straight at 0.3 m/s from its start pose; a non-zero angular.z curves it. The sim holds the last command until a new one arrives, so a --once publish keeps it moving; to stop it: 

ros2 topic pub --once cmd_vel geometry_msgs/msg/Twist "{}"

Useful checks:

ros2 node list                                   # exactly one /sim_robot
ros2 topic echo /odom --field pose.pose.position
ros2 topic hz /nvblox_node/static_map_slice      # ~1 Hz
ros2 topic pub -r 5 safety_layer/slack std_msgs/msg/Float32 "{data: 0.05}"   # shows up in the slack column

The sim does not check for obstacles: driving straight down the axis goes through the obstacle, which the plot shows as the path crossing the empty region. The sim stops and the launch exits at max_duration, whatever cmd_vel is still being published. Action chunks are logged whenever something publishes /vla/action_chunk; until then the chunk columns are zero and seq_num is −1, and the animation draws no chunk.

Run the chunk generator

In a third terminal, after the sim is up and before anything moves the robot:

ros2 run debug chunk_generator
ros2 run debug chunk_generator --ros-args -p goal_distance:=4.0

It waits for the first /odom message, latches the goal goal_distance metres ahead of the robot's pose at that moment (it logs Goal latched at ...), then publishes /vla/action_chunk at 8 Hz. Things to know:

  • The goal is fixed at the first odometry it sees. If the robot has already moved when you start the generator, the goal is relative to where it is then, and the log header's goal (computed from the start pose) will not match. Start the sim, then the generator, then whatever drives cmd_vel. For a new run restart both.
  • If you change goal_distance here, pass the same value to the sim launch (goal_distance:=...) so the plot draws the goal in the right place.
  • Stop it with Ctrl-C.
  • The chunks show up in the animation (pink line) and in the log's chunk columns.

Ready-made scenario: dy:=-0.5 dtheta:=0.3 starts the robot 0.5 m to the side, heading 17° toward the obstacle's centre (its straight line reaches x = 2.1 at y ≈ 0.07, inside the obstacle), so it is an angled approach, unlike the default head-on one. With no safety layer the robot drives straight through the obstacle, as the plot shows.

Run a safety layer

Start it last, after the sim and the chunk generator (the safety layer needs odometry, a chunk and the ESDF before it publishes anything):

# terminal 1: sim + ESDF                 (from the repo root)
ros2 launch debug sim_bench.launch.py controller:=cbf
# terminal 2: fake VLA
ros2 run debug chunk_generator
# terminal 3: the safety layer, with the bench ESDF's patch geometry
ros2 launch control CBF_safety_layer.launch.py patch_size:=44 patch_resolution:=0.05
# afterwards
python3 safety_layer_bench_testing/plot_run.py

Use MPC_safety_layer.launch.py and controller:=mpc for the MPC. The controller label only sets the slack axis units in the plot, so match it to what you run. Without the two patch arguments the safety layer uses the deployment defaults (22 cells at 0.1 m), which suit a 0.1 m ESDF; the recorded bench ESDF needs the values above. The debug nodes and the safety layer stop with Ctrl-C.

Solve time. Each safety layer node logs how long its solver call took, every tick, as an INFO line: [cbf_safety_layer]: solve_time_ms=0.741. It times only the solve (the CBF-QP, or the MPC's NLP), not the nominal command or the ESDF patch cut. To keep a log for comparison, tee the launch output and pull the numbers out: 

ros2 launch control MPC_safety_layer.launch.py 2>&1 | tee mpc_run.log
grep -o 'solve_time_ms=[0-9.]*' mpc_run.log | cut -d= -f2 > mpc_solve_ms.txt

Silence it with --ros-args -p print_solve_time:=false when using ros2 run. Why it renders fast

The ESDF image, contours, strip traces, legend and labels never change, so the script draws them once and keeps the pixels. Each frame restores those pixels and redraws only what moves (the path so far, the robot, the chunk, the text readout, three time cursors), then pipes the raw frame to ffmpeg. The generic matplotlib animation writer redraws and re-encodes everything each frame, which took about 225 ms per frame here; this takes about 16 ms.

14. Tuning the CBF

The CBF has few knobs, and they interact. This section says what each one does, how the current values were arrived at, and how to repeat the process with safety_layer_bench_testing/cbf_tuning.py.

What the knobs do

The filter solves, every tick, for the [v, omega] closest to the nominal command that keeps a barrier non-negative. The barrier is h = (ESDF distance at a point LOOKAHEAD_M ahead of the robot) − (margin), and the condition is dh/dt ≥ −alpha·h: as the robot gets close, it may only close in ever more slowly.

KnobValueWhat it doesRaise itLower it
CBF_EXTRA_MARGIN_M0.15 Added to SAFETY_MARGIN_M (0.20) to make the barrier's margin (0.35). The barrier watches a point ahead of the robot, so the robot's centre can be closer to an obstacle than the barrier says; this covers that. The centre stays farther out (0.20 extra: min centre 0.269 m instead of 0.206 m). More conservative in tight spaces; brakes earlier. The centre dips inside the real margin: with 0 extra it spent 11–13 % of a run inside 0.20 m.
LOOKAHEAD_M0.4 How far ahead of the robot the barrier is evaluated. Turning moves that point sideways by lookahead × omega, which is what gives omega any effect on the barrier. At 0 the filter could only brake. More steering authority and earlier reaction; more conservative. The lookahead plus the margin must fit inside the ESDF patch (0.75 m of a 1.1 m half-patch now). Less steering authority. At 0.1 m, with the omega weight at 1, none of 4 start poses reached the goal.
CBF_WEIGHT_OMEGA (vs CBF_WEIGHT_V = 1)0.003 The cost of changing omega from the nominal, relative to changing v. The nominal is obstacle-blind and keeps pointing at the obstacle. The filter prefers braking to steering. At 1.0 the robot stops in front of the obstacle and stays there (0 of 5 start poses reached the goal). The filter steers freely round the obstacle. Below about 0.01 it makes no measurable difference.
CBF_ALPHA2.0 How fast h may shrink. It sets how hard the filter brakes on the way in, and how hard it pushes out once inside the margin. Brakes later and harder. Slack starts to be used (max 0.009 at 2, 0.080 at 3, 0.24 at 6). Brakes earlier and gentler.
CBF_SLACK_WEIGHT1000 The price of violating the barrier. It only matters when the barrier cannot be met (the robot is already inside the margin). 10 to 100000 made no difference in the sweeps, which were run with the omega weight at 1, where the robot stalls either way. Not re-checked with the current omega weight.
PP_K_CURV (common)1.0 Not a CBF knob: it is the pure-pursuit nominal's slowdown in curves, v = V_MAX / (1 + K·|curvature|). It matters here because the CBF filters that nominal. Slower through detours. Modestly faster: 0.5 took the runs that reached the goal within 30 s from 12 to 14 of 15 (section 14 below).
SAFETY_MARGIN_M, V_MAX, OMEGA_MAX (common)0.20, 0.3, 0.3 Physical: the robot's half-width plus clearance, and the platform limits. Shared with the MPC; not tuning knobs. The omega limit bounds how fast the filter can steer.
The two tensions to remember. (1) Safety filter versus progress: the more the filter is allowed to brake and the less it is allowed to steer, the more the robot stops in front of obstacles. Omega weight and lookahead set that balance. (2) The barrier watches a point ahead, the margin is about the centre: extra margin is what closes that gap.

The process

  1. Say what good means, as numbers. For each run: the share of time the robot's centre is inside the 0.20 m margin, the smallest centre distance, whether it stalled or reached the goal, the slack used, and the smallest barrier value. Judge the centre, not the barrier: the margin is a property of the robot.
  2. Make the loop fast. A ROS run takes 35 s. cbf_tuning.py replays the sim, the chunk generator and the CBF node offline using the same code, so a run takes about 0.4 s and 15 start poses about 6 s. verified It reproduced a ROS run before it was trusted: minimum centre distance 0.112 m in both, maximum slack 0.351 versus 0.354, final distance to goal 0.28 m in both.
  3. Look inside a bad run before touching a knob. The first run had the centre inside the margin 25–30 % of the time. The timeline showed the barrier at −0.14 while the filter was still commanding full speed and paying 0.35 of slack. That could not be optimal, so the solver was checked against an independent solve of the same QP (identical), and the QP's coefficient on forward speed was printed: it was about 0. That was the derivative defect (section 5), not a tuning problem. Tuning around it would have hidden it.
  4. Fix, then re-measure. With the derivative fixed the margin held (0 %), but the robot now stopped in front of the obstacle: a correct filter with a blind nominal pointing at the obstacle has nothing pushing it sideways.
  5. Sweep one knob, then several together. Alpha and the slack weight did nothing for progress. Lookahead of 0.4 m and above helped a little (1 of 4 poses reached the goal instead of 0). The omega weight was the lever: low values let the filter steer round the obstacle and every start pose reached the goal, at the price of the centre dipping inside the margin (11–13 % of a run).
  6. Understand the cost before paying it. That dip is geometry (barrier ahead, margin about the centre). Two answers were tried: a second barrier on the centre (rejected: the robot parked against the margin and did not progress), and a larger margin on the lookahead barrier (adopted).
  7. Check that the choice is not fitted to the poses used. The chosen values were then run on 15 start poses (the sweeps used four to six): 0 % inside the margin, none stalled. The runs that did not reach the goal in 30 s were checked and were still moving at full speed 1.1–1.9 m short, on longer detours; they were not stalls.
  8. Confirm in ROS with the real nodes and the sim (section 13), and compare with the offline numbers.

# MPC obstacle avoidance — investigation and verdict

**TL;DR:** this branch's NMPC obstacle-avoidance formulation reliably deadlocks
(stops rather than detours) when an obstacle sits close to dead-on with the
reference path. Every fix tried either didn't work, worked but was unsafe,
worked but wasn't architecturally defensible, or worked but was too slow to
run in real time. We're ruling out this formulation for now and moving to a
CBF-QP safety filter instead (`CBF-obstacle-avoid` branch), which solves the
same scenario cleanly on effectively the first attempt. This document is meant
to be enough to reproduce every claim below without re-deriving it.

## The problem

`UnicycleMPC` (`src/control/control/mpc_imp/solver_setup.py`) tracks a VLA
action chunk while keeping a slacked ESDF-distance margin around obstacles
(`SAFETY_MARGIN_M`). With an honest cost function (DARE-derived terminal cost,
no artificial weight inflation) and a prediction horizon sized to match the
VLA chunk's own span (`N=14`, `PREDICTION_DT=0.2` → 2.8s, vs. the chunk's
~2.67s), the solver finds it optimal to **stop** in front of an obstacle that
sits close to the reference line's own centreline, rather than detour around
it. A small initial detour sometimes happens, then it settles into a static
equilibrium a short distance short of the obstacle.

Reproduce this directly:

```
source install/setup.bash
python3 mpc_dev_artefacts/mpc_replay.py --horizon-n 14
# SUMMARY final_x=1.676 max_slack=0.0461 n_fail=0/250 stalled=True
```

(`final_x=1.676` is well short of the obstacle, which sits around
`x=2.0-2.2`; `stalled=True` means the last quarter of the run moved less than
5cm.)

## Root cause

The terminal cost is the only thing that could reward *having completed* a
detour — stage costs only reward the act of tracking, not having made net
progress. But the terminal state is scored against the VLA reference, which
is generated by an obstacle-blind fake VLA (`chunk_generator.py`) that keeps
re-aiming at a fixed lookahead point on the original line every tick,
regardless of what the robot does. With a horizon that (correctly, on
principle) doesn't extend past what that reference actually covers, the
terminal target stays pinned near/on the obstacle for as long as the robot is
near it. So there's never a horizon-visible reward for finishing the
maneuver — stopping and a hypothetical clean detour cost the solver
identically nothing extra in constraint violation, and nothing in the visible
window favours one over the other.

## What we tried, in order

| # | Attempt | Result |
|---|---|---|
| 1 | `QF_MULTIPLIER=100` (terminal cost cranked) | Detours, but pays for it — heavy slack ("margin") abuse, not a clean detour |
| 2 | Reverted to honest `Qf` (DARE value, multiplier=1) | Deadlock returns |
| 3 | ESDF patch-size/resolution bug found & fixed (`PATCH_SIZE` 22→44) | Real bug (patch covered half the area the solver assumed at this bag's resolution), independent of the deadlock question, but was confounding every other experiment until fixed |
| 4 | ESDF out-of-domain query bug found & fixed | `ca.bspline` returns exactly `0` for a query outside the patch's knot domain regardless of coefficients — read as "touching an obstacle." Fixed by shifting coefficients by `∓NVBLOX_MAX_DISTANCE_M` so out-of-domain reads as free space instead. See `_query_distance`/`pack_params` in `solver_setup.py`. |
| 5 | Reference held static past chunk span → terminal target pinned on the obstacle. Fixed: linear extrapolation of the reference tail instead of holding it | Real fix, but small in practice (horizon only barely exceeds chunk span at `N=14`) |
| 6 | Horizon extended well past the reference's own span | Breaks the deadlock, but rejected on principle — fabricates reference data the real system doesn't have (see below) — and at extreme lengths caused severe dithering (plan flip-flopping between detour directions tick to tick, no failures, just instability) |
| 7 | "Vortex" reward: smooth, handedness-agnostic reward for velocity tangential to the ESDF gradient, giving a local (non-terminal-cost) reason to curve away early. Exponential decay with distance | **Unsafe.** Reward for going deeper into the obstacle grows exponentially, slack penalty only quadratically — for any finite weight the reward eventually wins. Caused the robot to plan straight through the margin. |
| 8 | Same vortex idea, linear decay (bounded, safe) | Swept weight 5→3000 and decay-scale 0.3→1.0m, alone and combined with modest `Qf` multipliers (1-10x): every combination either still stalled (with small bounded slack) or, at the extreme end, produced **unstable oscillation** — the trajectory swept up, stalled, reversed, swept down past the line, stalled again, then started moving backward in x. Never converged to a clean single detour. Fully removed from the code — this is dead, don't resurrect it. |
| 9 | Move suppression (rate penalty on `Δu`, to fight dithering from #6) | Same failure pattern as #1/#7: made sharp turning relatively more expensive than eating margin, so it just shifted the deadlock↔slack-abuse tradeoff again rather than fixing anything |
| 10 | Near-miss reference line instead of dead-on (tilted ~-4.6°, so the line clips the obstacle's edge at ~0.10m clearance instead of driving through its centre) | **Plain, unshaped MPC handles this cleanly** — `stalled=False`, `max_slack≈0.01`, smooth single correction, full speed maintained throughout. Confirms the dead-on/near-exactly-symmetric case is close to worst-case for this failure mode, not representative of typical obstacle placement. |
| 11 | Dead-on case again, horizon bumped until it converges | Converges reliably from `N≈44` (`~8.8s`, over 3x the chunk's own span) upward — see next section. The transition isn't a clean threshold: `N=41` worked with some solve failures, `N=42-43` stalled again, `N≥44` reliably clean. |

Attempt #10's mp4 and #11's mp4 are both in this repo (see Evidence below).

## Why #6/#11 (longer horizon) isn't the answer, even though it "works"

Three independent problems, each sufficient on its own:

1. **Architectural.** It only works by scoring the terminal state against a
   reference that's linearly extrapolated far past anything the real VLA
   chunk committed to. That's fabricating information the real system doesn't
   have, not a defensible fix.
2. **Reliability.** At the extreme horizons tried earlier in this
   investigation (well past what's needed for the dead-on case alone), the
   same fix that cures the deadlock introduces multi-modal dithering instead.
3. **Computational — measured directly, not assumed.** Even the *moderate*
   horizon that reliably fixes the dead-on case (`N=50`) is too expensive to
   solve within the real 66.7ms (15Hz) control budget, specifically during
   the part of the maneuver that matters most:

   ```
   N=14: mean solve=10.8ms  max=11.7ms   (budget=66.7ms)
   N=44: mean solve=46.1ms  max=48.5ms   (budget=66.7ms)   <- free-space benchmark
   N=50: mean solve=52.1ms  max=60.0ms   (budget=66.7ms)   <- free-space benchmark
   ```

   That's the easy case (no active constraint). Timed tick-by-tick during the
   *actual* dead-on maneuver (obstacle constraint genuinely engaged, harder
   for IPOPT's interior-point method to navigate):

   ```
   N=50, real maneuver: mean=70.9ms max=423.2ms  budget=66.7ms
   24/90 ticks (27%) over budget, worst case 6.3x the control period
   ```

   This is exactly what produces the visible stopping/stuttering in
   `mpc_plotter_deadon_N50.mp4` — `cmd_vel` only updates when a solve
   finishes, not on a steady beat, so slow ticks mean the robot keeps
   executing a stale command for up to ~400ms before the next update lands.
   The underlying trajectory math is fine (the headless replay, which has no
   real-time constraint, shows a clean single detour); the real-time
   execution of it is not.

Reproduce the timing numbers:

```
source install/setup.bash
# free-space benchmark, all three horizons
PYTHONPATH=src/control python3 -c "
import time, numpy as np
from control.mpc_imp.solver_setup import UnicycleMPC
from control.mpc_imp.constants import CONTROL_LOOP_DT
for n in [14, 44, 50]:
    mpc = UnicycleMPC(N=n, M=n, safety_margin=0.20)
    x0=[0.,0.,0.]; x_ref=np.tile([1.,0.,0.],(mpc.N+1,1)); u_ref=np.tile([0.2,0.],(mpc.N,1))
    patch=np.full((mpc.patch_size,mpc.patch_size),2.0)
    mpc.solve(x0,x_ref,u_ref,0.0,patch)
    ts=[]
    for _ in range(10):
        t0=time.perf_counter(); mpc.solve(x0,x_ref,u_ref,0.0,patch); ts.append(time.perf_counter()-t0)
    print(f'N={n}: mean={np.mean(ts)*1000:.1f}ms max={np.max(ts)*1000:.1f}ms')
"
```

## Why MPC normally works for this class of problem, and what's different here

MPC-without-an-obstacle-aware-reference is a standard, working technique in
general. What's specific to this setup:

- **The reference here is short and constantly re-anchored**, not long and
  merely dumb. Most working deployments have an obstacle-blind reference that
  persists far beyond any reasonable control horizon (a lane centreline, a
  pre-planned global path), so horizon length is chosen from maneuver
  dynamics alone, independent of reference availability. Here the reference
  is a VLA action chunk (~0.8m / 2.67s) regenerated from scratch every
  ~125ms, always re-aiming at a fixed point on the original line — tying the
  horizon to "don't fabricate reference data" and "long enough to see a
  maneuver" become the same constraint, which is what pins the terminal cost
  through the obstacle.
- **Avoidance here rests entirely on cost-shaping inside one horizon**, with
  no anticipatory mechanism that's active independent of the cost tradeoff
  (no terminal invariant set with a recovery controller, no hard/CBF-style
  per-step constraint). Every fix in this document reduces to "which side of
  a stop-vs-detour cost competition wins," because that's the only lever
  available.
- **The test obstacle sits almost exactly on the reference's centreline**,
  close to worst-case for any gradient-based local method (attempt #10 shows
  the plain formulation handles a realistic near-miss cleanly).

Formulations worth trying if this gets revisited, roughly in order of
promise (none implemented here):

1. **MPC-CBF hybrid** — embed a discrete-time CBF condition
   (`h(x_{k+1}) - h(x_k) >= -alpha*h(x_k)`) as a *constraint* at every step of
   the horizon, using the look-ahead-point barrier already built on the CBF
   branch (`cbf_qp.py`) so `omega` has real authority. Keeps genuine
   multi-step lookahead while inheriting the CBF's core property: the
   constraint doesn't need convincing a maneuver pays off, it just has to
   hold at every predicted step. Doesn't touch the reference. (Zeng, Zhang &
   Sreenath, "Safety-Critical Model Predictive Control with Discrete-Time
   Control Barrier Function".)
2. **Safe-corridor / free-space decomposition** — compute convex free-space
   regions from the ESDF map (independent of the reference) and constrain the
   trajectory to stay inside them, resolving "which side" combinatorially
   before the continuous solve runs.
3. **Multi-hypothesis warm-starting** — solve from two initial guesses
   (assume-left / assume-right) each tick, take whichever is feasible/cheaper.
   Directly attacks the symmetric-tie problem at ~2x compute cost, no
   cost-function changes.

## Reproducing / sweeping further

`mpc_dev_artefacts/mpc_replay.py` is the tool used throughout this
investigation — a headless closed-loop replay against `esdf_single_obs`,
re-importing the solver fresh each run so `constants.py` edits take effect,
with no real-time constraint (fast for sweeping, but see the timing section
above for why it can't surface solve-time problems on its own). Requires
`source install/setup.bash` and the `control`/`debug` packages built.

```
python3 mpc_dev_artefacts/mpc_replay.py                     # current constants.py as committed
python3 mpc_dev_artefacts/mpc_replay.py --horizon-n 14       # reproduce the original deadlock
python3 mpc_dev_artefacts/mpc_replay.py --horizon-n 44       # near the convergence threshold
python3 mpc_dev_artefacts/mpc_replay.py --qf-multiplier 100  # reproduce the early Qf-cranking experiment
python3 mpc_dev_artefacts/mpc_replay.py --verbose --ticks 90 # tick-by-tick trace
```

Current committed `constants.py` reflects the `N=50` dead-on test (item #11
above) — this is not the recommended production configuration, it's the last
state tested before ruling the approach out. If picking this branch back up,
start by reading this document, not just the code.
